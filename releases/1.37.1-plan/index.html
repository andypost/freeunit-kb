2026-10-11 (late) — the Change: entries are now THREE; decision text ready

Live state re-read from origin/master (44bda7b8): 98 commits past the 1.37.0 tag, version still 1.37.0 / 13700, the 1.37.1 section carries 24 entries — 21 Bugfix + 3 Change (the earlier note counted two), section header still dated 04 Oct 2026.

The third Change: is new since that note: "the Wasmtime library of the wasm module is now built without the component-model C API. The module loads core WebAssembly modules only and never called that API. libwasmtime.so shrinks from 32.4 MB to 23.6 MB and no longer exports the 156 wasmtime_component_ functions…"*.

Class of each entry under the project's own rule (patch = security/DoS and regressions only; features, API and behaviour changes go to a minor):

#EntryWho observes itClass
1--otel no longer needs OpenSSL; configure stopped with "OpenTelemetry support requires OpenSSL" and unitd linked OpenSSL without --openssla build that previously failed now succeeds; the linked library set changesbuild/dependency — re-wordable as Bugfix
2a TLS failure caused by the client is logged at info instead of alertoperators: log severity, alerting rules keyed on alertruntime behaviour — the one genuine behaviour change
3the bundled Wasmtime for the wasm module drops the component-model C APIwhoever links libwasmtime.so: 8.8 MB smaller, 156 exports removedbuild/dependency + shipped-library export surface — re-wordable as Bugfix if the component-model module is unaffected

The check that makes entry 3 safe: Component Model support in Unit is a separate Rust module (src/wasm-wasi-component, a crate over wasmtime+wit-component) and is a documented, promoted feature since upstream 1.32 (the docs carry a two-part blog series on it). The C wasm module is the one that never called the removed API. So the claim holds only if the wasm-wasi-component build/test leg is green on the release commit — run that leg before deciding, and say so in the entry.

Recommendation. Keep 1.37.1 a patch with no policy exception: re-word (1) and (3) as Bugfix: (both are build/dependency corrections with no runtime capability change once the component leg is proven), and treat (2) as the single judgement call — either keep it as a Change: and accept one change-carrying patch with a line in the announcement ("TLS failures caused by the client are now logged at info; adjust alert rules keyed on alert"), or move (2) to 1.38.0 and ship a spotless patch. The strict-policy alternative is to move (2) and (3) together; that costs the size win and is not required by the wording of the rule.

Still mechanical, unaffected by this decision: version → 1.37.1 / 13701, the section header date, the tag, release-docker/unitctl/build-deb/build-distros, artifact pull-verify, the Alpine aport rebase, and #586's retarget to master.

3. Mechanics

  • Merge order: test-only first (#579, #580), then product fixes (#581, #582, #583, #584, #573, #576).
  • Every PR inserts at the TOP of the 1.37.1 section → each later merge conflicts in CHANGES/docs/changes.xml. Resolution is mechanical: keep both entries. Verified by test-merge: independent merges clean, cumulative conflict only in the changelogs.
  • #584 is the one PR that is NOT green: its own regression test test/test_http_header.py::test_http_header_large_buffers_above_255 fails on test (python-3.12, ubuntu-latest) — the test sets header_buffer_size, which master's config validator rejects (Unknown parameter "header_buffer_size" / suggestion body_buffer_size). So the test was written against a tree carrying a setting master does not have: #584 needs its test fixed (or the accompanying option landed) before merge. MERGEABLE alone is not a merge verdict.
  • Then: bump version → 1.37.1 / 13701; tag; run release-docker, unitctl, build-deb, build-distros; verify artifacts by pulling them (docker pull, unitctl --version, a deb install), not by a green pipeline.
  • Definition of done for the trigger: a green musl/Alpine build + test run of the release, and the aports aport rebased onto the tag.
