TLS abstraction & kTLS in FreeUnit

Scope: freeunitorg/freeunit (C core), master @ 2026-10-11. Read at code level, not from web search. Every claim below carries a file:line citation.

Verdict up front:

  • Variant A (multi-backend nxt_tls.h) is much smaller than it looks: ~2–3 weeks.

The vtable skeleton already exists; the coupling surface is ~15 call sites, and most of them already go through a function pointer. The genuinely backend-specific work is confined to nxt_openssl.c.

  • kTLS is orthogonal and does NOT belong in the variant-A branch. It is a

data-path change behind the same interface, gated by a kernel probe, and it collides with FreeUnit's multiprocess + sendfile model in ways variant A never touches. Two independent tracks.

  • No reason found to revisit variant B (TLS out of process). The hot path is

unchanged by A; B would put serialisation + IPС on every record. Not reopened.

1. Current state of nxt_tls.h and nxt_openssl.c

1.1 src/nxt_tls.h (114 lines) — already a partial vtable

The header is NOT raw OpenSSL. It already declares an opaque, backend-neutral interface. Inventory:

Key observation: the abstraction is half-built and asymmetric. nxt_tls_lib_t has only the lifecycle hooks (init/free of the library and of a server config). The data path is not in the vtable at all — it lives in two other places:

  • nxt_tls_conf_t.conn_init — a function pointer the core calls to attach TLS

state to a connection (nxt_h1proto.c:419).

  • nxt_conn_io_t — a core vtable (nxt_conn.h:45–93) that the OpenSSL backend

swaps in wholesale at nxt_openssl.c:1242 (c->io = &nxt_openssl_conn_io;).

So today there are three indirection points, not one: the lib lifecycle vtable, the per-config conn_init pointer, and the connection's io vtable. A real multi-backend design must decide whether to unify these or (better) leave nxt_conn_io_t as-is and just add the backend's conn_init+io swap behind the existing nxt_tls_lib_t.

2. How the core uses nxt_tls_conf_t — the real coupling surface

Two questions matter: (a) is nxt_tls_conf_t used only as config storage, or do core files reach into TLS-specific functions? (b) which of these go through an indirection already?

2.1 The NXT_TLS guard sites across the core

NXT_TLS appears in: nxt_main.h, nxt_runtime.h, nxt_router.h, nxt_router.c, nxt_h1proto.c, nxt_conn.h, nxt_conn_write.c, nxt_listen_socket.h, nxt_listen_socket.c, nxt_process.h, nxt_main_process.c, nxt_conf_validation.c, nxt_controller.c, plus src/test/nxt_main_store_test.c. That is the blast radius of the compile-time guard — 14 core files (+1 test), the ones that would carry a runtime lib pointer instead of #if.

Finding: there are NO direct calls into OpenSSL-typed functions from outside nxt_openssl.c. Grep for SSL_*/X509_*/BIO_* outside the backend returns nothing. The core touches:

  • an opaque pointer (c->u.tls, socket_conf->tls),
  • two function pointers already (lib->server_free, conf->conn_init),
  • one struct field by name (->bundle, at nxt_router.c:2661 and in

nxt_openssl_server_init).

The one leak is nxt_router.c:2661 reading skcf->tls->bundle directly. That is the only place the core dereferences a field of nxt_tls_conf_t for a decision, and it can be replaced by a boolean on the conf or a vtable predicate.

Conclusion for the effort question: the "real work to move behind a clean interface" is essentially (1) add the missing data-path hooks to nxt_tls_lib_t (today: only lifecycle + conn_init), (2) replace the #if (NXT_TLS) guard with a runtime rt->tls != NULL where a second backend must coexist, (3) fold conn_init into the vtable, (4) remove the single ->bundle reach-through. Not a rewrite.

4.1 Precedent in-tree: nxt_wasm_operations_t

The WASM backend is the template. nxt_wasm.h:35,131-134 declares nxt_wasm_operations_t with .init/.destroy/.exec_request/.exec_hook, and nxt_rt_wasmtime.c:584 binds nxt_wasm_ops. The pattern the TLS work should copy: one _operations_t struct, one extern const instance per backend, one nxt_service_get selection. nxt_tls_lib_t is already 80% of this; it just needs the data-path slots.

4.2 Precedents elsewhere (event-driven C servers)

  • nginx: ngx_ssl_* is OpenSSL-coupled but selects at build

(--with-openssl), never multi-backend at runtime. LibreSSL works via ABI compat, not a second driver.

  • HAProxy: OpenSSL and LibreSSL/BoringSSL supported via build-time

USE_OPENSSL/USE_LIBRESSL; compatibility shims in include/haproxy/ssl_* (HA_OPENSSL_VERSION_NUMBER, HA_USE_*). Closest match to variant A.

  • curl: a real vtls layer (Curl_ssl_backend struct, vtls/) with per-backend

files — the full vtable form, but curl's I/O model is far simpler than Unit's.

  • Postfix: OpenSSL-only, build-selected.

Take-away: HAProxy's "build-time select + shim header" is the pragmatic model; curl's full vtable is the aspiration. FreeUnit's nxt_tls_lib_t sits between them and needs only the data-path slots.

5. kTLS — where the data path is, and how it would attach

5.1 The data path today

The per-connection TLS data path is entirely inside nxt_openssl.c:

  • Read: nxt_openssl_conn_io_recvbuf (1368) → SSL_read (1379).
  • Write: nxt_openssl_conn_io_send (1419) → SSL_write (1430), reached from

nxt_openssl_conn_io_sendbuf (1403) and from the core's generic send path nxt_sendbuf.c:258 (c->io->send(...)).

  • Attach point: nxt_openssl_conn_init (1197) swaps c->io = &nxt_openssl_conn_io

(1242). This is the single seam where a kTLS build would instead install a kTLS nxt_conn_io_t (or leave the kernel path and skip the userspace record loop).

After handshake, kTLS moves the record layer into the kernel (setsockopt(sock, SOL_TLS, TLS_TX/TLS_RX, …)); the userspace SSL_read/SSL_write then speak plaintext to a kernel-transformed socket. In FreeUnit terms: the post-handshake recvbuf/sendbuf hooks become plain read/write/sendfile, and nxt_openssl_conn_io_send's SSL_write is bypassed.

5.2 sendfile × TLS today

Critical finding: TLS disables sendfile on purpose. nxt_openssl.c:1243 sets c->sendfile = NXT_CONN_SENDFILE_OFF; at conn init, and the OpenSSL nxt_conn_io_t (nxt_openssl.c:169-177) has no old_sendbuf slot.

The generic (non-TLS) send path proves the contrast at nxt_conn_write.c:201-202: a bare file buffer is routed to nxt_conn_io_sendfile() → nxt_sendfile() (the zero-copy kernel path, nxt_conn_write.c:222). Under TLS that dispatch never happens: c->io is the OpenSSL vtable, whose sendbuf (nxt_openssl.c:1403) coalesces into memory and calls SSL_write (:1430). Per nxt_sendbuf.h:10-13, "file buffers must be read in memory in advance" on any backend without a sendfile slot.

Implication: static files over TLS today cost a userspace read + encrypt + copy per record, in NXT_TLS_BUFFER_SIZE (4096) chunks. kTLS is precisely the fix — with kernel TLS, sendfile() (or SSL_sendfile on OpenSSL ≥3.2) can push file pages through kernel crypto and skip the userspace record loop. This is exactly why the task links kTLS to "static".

5.3 Minimum OpenSSL and the SCM_RIGHTS / multiprocess risk

ItemFinding
OpenSSL floor1.1.1 (auto/ssltls:48-67, and the comment at :36-44 keeps it there for RHEL 8). But SSL_sendfile (the clean zero-copy TLS-static path) needs OpenSSL ≥ 3.2. So kTLS via SSL_sendfile would set a second, higher floor for kTLS users only — or FreeUnit drives sendfile() directly after TLS_TX is set, no SSL_sendfile needed (Linux kTLS offloads the socket; a plain sendfile to it works). Recommendation: drive plain sendfile() post-TLS_TX, keep the 1.1.1 floor.
KernelkTLS needs CONFIG_TLS/tls module (Linux 4.13+; aarch64/uDP offload later). Must be probed at build (auto/ similar to auto/sendfile) and at runtime (the module may be absent) — build probe alone is not enough.
CipherskTLS supports AES-GCM-128/256, AES-CCM-128, ChaCha20-Poly1305, SM4 (SM4 needs ≥5.1 + crypto). Ciphers outside this set silently fail TLS_TX → must fall back to userspace. Config surfacing: an explicit opt-in "tls": {"ktls": true} on the listener (NOT auto-enable), because it changes cipher availability and the support matrix.
Multiprocess / SCM_RIGHTSThe real risk. FreeUnit passes listening sockets main→router via SCM_RIGHTS. A kTLS-enabled socket carries the TLS_TX/TLS_RX socket options and the per-socket crypto state in the kernel, tied to the socket. Two concerns: (a) the TX/RX transformation is installed after handshake, per accepted connection, so it is on the accepted fd, not the listening fd — SCM_RIGHTS of the listening socket is unaffected; (b) if any accepted connection fd is passed between processes (FreeUnit's router↔app uses the port/queue plane, not raw accepted sockets, for HTTP apps — but proxy peers and some paths may hold fds), the kTLS state travels with the fd, which is fine on Linux but must be verified — a TLS_TX socket that crosses a process boundary keeps its offload. Handshake must still run in userspace (kTLS has no userspace handshake API on the listen side without kTLS handshake offload, which is not in mainline). So the multiprocess model is compatible but the handshake→offload handoff must be per-connection.
HandshakekTLS offloads the record layer only; the handshake stays in userspace via OpenSSL (or an in-kernel handshake helper where available). FreeUnit's handshake already runs in the router process per connection — so the kTLS install step slots right after nxt_openssl_conn_handshake completes.

6. Verdict: one branch or two tracks?

Two independent tracks, in this order:

  1. Variant A first (A1–A2, ~1 week; +A5 for LibreSSL, ~2 weeks total). It is a

pure interface refactor, ships no new runtime surface, and lets the core stop #if-ing on TLS. It also enables kTLS by giving the data path a clean seam (K3's kTLS nxt_conn_io_t plugs into the same c->io swap that A1 formalises).

  1. kTLS second, on top of A (K1–K6). It is orthogonal — a data-path

implementation behind the interface A produces — but it carries its own support matrix (kernel module, cipher set, a new runtime-env CI), which must not block A's release cadence.

Combining them is wrong because: A is build-time/interface, kTLS is runtime/kernel+data-path; A has no CI-env dependency, kTLS needs a real kernel module; A touches 12 guard sites, kTLS touches the nxt_conn_io_t swap + auto/

  • cipher validation. Different reviewers, different failure modes. One issue each,

A tagged for the next minor, kTLS tagged as a spike→feature with its own kernel-gated test job.

7. Open question for discussion (not decided here) — variant B

No codepath found that forces revisiting variant B (TLS out of process). B would add serialisation + an IPC round-trip to every SSL_read/SSL_write, i.e. on the hot path, for a benefit (process isolation of the TLS backend) that the in-process vtable already gets by other means (backend is compiled into unitd, no dynamic plugin boundary). Returning as an open question: is there a regulatory/FIPS motivation for B (swap crypto module per deployment)? If not recommended, B stays closed. No technical reason found to reopen it.

Kernel-doc check via Context7 (2026-10-11)

Context7's public API (https://context7.com/api/v1/search?query=…, then …/api/v1/<id>?type=txt&topic=…&tokens=N, keyless) was queried against the Linux kernel documentation corpus (/websites/kernel_doc_html). It confirms two load-bearing claims of this page:

  • sendfile() works on a kTLS socket. The kernel doc states it plainly: "Send file data with sendfile(): uses sendfile() to send a file's data over TLS records of maximum length (2^14)". So the recommendation above holds — drive plain sendfile() after TLS_TX and keep the OpenSSL 1.1.1 floor; SSL_sendfile (and its ≥3.2 floor) is not needed.
  • The cipher parameters are handed to the kernel, not negotiated there: the doc's example fills crypto_info.info.cipher_type = TLS_CIPHER_AES_GCM_128 plus iv/rec_seq/key and sets them with setsockopt(SOL_TLS, TLS_TX/TLS_RX) after the handshake completes — which is exactly why the cipher gate and the "install the offload right after nxt_openssl_conn_handshake" step are the right shape.

One new constraint found, worth a line in the plan: with device offload, sendfile() data must not be modified while the transfer is in flight ("Enable zero-copy transmission of sendfile() data directly to the NIC when device offload is enabled. The application must ensure the data is not modified…"). FreeUnit's buffer lifetime rules for the sendbuf path have to be checked against that before device offload is offered.

One new open item: the kernel doc also documents sendmsg() with TLS_SET_RECORD_TYPE — sending a TLS control message (alert, handshake) over a kTLS socket by giving the record type in a SOL_TLS control message. FreeUnit's shutdown path calls SSL_shutdown (close_notify); whether that alert travels correctly once TLS_TX owns the record layer, or must be sent as such a cmsg, is exactly the kind of thing a spike must answer.

Not verified there: SSL_sendfile and its OpenSSL ≥3.2 requirement — Context7's OpenSSL corpus (design docs and man sources) returned zero hits for SSL_sendfile, kTLS and TLS_TX on every topic tried, so that claim still rests on the API documentation alone. It is not on the recommended path.

Measurement environment — resolved: the TLS ULP is the gate (measured 2026-10-11)

An earlier entry here said kTLS "cannot be exercised on the coordinator" and left the cause undecidable. Both are retracted: the failure was a missing documented step, and it was the probe's bug, not the kernel's.

setsockopt(SOL_TLS, TLS_TX, …) alone never reaches the TLS code. The kernel documentation requires the TLS ULP first, after the connection is established — setsockopt(SOL_TCP, TCP_ULP, "tls"), "Setting the TLS ULP allows us to set/get TLS socket options" — and net/tls/tls_main.c shows why: tls_init(sk) is the ULP's .init, it refuses with -ENOTCONN unless TCP_ESTABLISHED, and it is what creates the tls_context and swaps sk_prot. Without it, the socket layer answers the generic ENOPROTOOPT (92) — the same errno an unknown level gets, which is exactly why the negative looked like a kernel property.

Measured (kernel 6.8.0-136-generic locally; ubuntu-24.04 / 6.17 and ubuntu-22.04 / 6.8 in CI, both legs green): after TCP_ULP=tls the option is accepted, the peer receives 1703030033 (application_data record) with the plaintext absent, and sendfile() drives the kTLS socket. Cost, measured on CI (runs 38170196534 and 38170607310, both legs green), normalised per MiB of plaintext:

Armsystem CPU / MiBthroughput
plaintext socket0.29–0.37 ms2 875–4 345 MiB/s

kTLS is ~2.4× slower than a plaintext socket — that is the price of AES-GCM in the kernel, not a verdict. Against the path it would replace (userspace OpenSSL) it is 17.7–21.0× the throughput with 3.2–4.5× less system CPU and roughly 30× less user CPU per MiB, on two kernels (6.17, 6.8) and two OpenSSL versions (3.0.13, 3.0.2). Caveat that bounds it: the OpenSSL arm is Python-driven, so it sets the floor of the userspace path — a C driver narrows the multiplier while leaving the structure kTLS removes (one read + encrypt + copy per 4 KiB record). Device offload was not exercised. Full method, runs and caveats: docs/exp/ktls-verdict.md.

Key path — a real TLS 1.3 session handed to the kernel (measured 2026-10-11)

The socket options are the easy half; the key material is the half that decides whether a kTLS data path can exist. Two facts the C side must be built on:

  1. The application-data record sequence of TLS 1.3 starts at 0 — the sequence is per key epoch,

so handshake records do not offset it. Nothing has to count handshake records.

  1. The kernel's records, built from keys derived outside OpenSSL, are accepted by OpenSSL

unchanged: the interface between the stacks is the key material, not a callback.

Open item, not a claim: on both CI images TCP_ULP=tls answered EEXIST before the probe was fixed (the local kernel answered success) — something in that stack had already attached the TLS ULP. The probe now treats EEXIST as the state TLS_TX needs, which is what it is, but the cause is not established and the ULP state is not printed on the success path.
