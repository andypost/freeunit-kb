_response_complete() - why it is safe

It returns True only for a response whose own framing says it is whole (Content-Length reached, or chunked with a 0 chunk and its CRLF). Everything else - no Content-Length and no chunked, a Content-Length it cannot parse, chunked with trailers, a coding list that only ends in chunked (it uses value.lower().endswith(b'chunked')), and any bodyless response (HEAD, 1xx, 204, 304, which it documents as out of scope) - returns False, and the read then ends on read_timeout exactly as before. A body that is short of its declared Content-Length never looks complete, so the helper cannot hide a truncated response; it only skips the wait when completeness is provable.

The shard guard

if [ "${#owner[@]}" -ne "$n" ] fires when a shared file has no owner or two files collapse onto one key, i.e. it is a duplicate/omission net inside one leg. The property "each shared file is in exactly one shard across the three python legs" holds by construction instead: all three legs derive the same map because versions = length(.runtimes.python) and shard = index of this leg's version come from the same pkg/eol.json, and the assignment loop is deterministic. The heavy-file weights are a hardcoded list from one run and must stay sorted descending for the greedy least-loaded choice to balance well; a stale weight costs balance only.
