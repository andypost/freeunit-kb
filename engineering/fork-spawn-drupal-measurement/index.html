fork-spawn × Drupal: measured (kernel+cron, and the stub tick)

Date: 2026-09-12 · Status: measured live on a rootless unitd 1.36.1 + PHP 8.4.25 Artifacts: tools/artisan_stubs/fork_spawn.php, tools/artisan_stubs/drupal_boot_cron.php, tools/artisan_stubs/drupal_stub.py · Stand: tools/setup-fu-stand.sh / start-fu-stand.sh

Two questions, both answered with real numbers:

  1. does a real Drupal bootstrap (DrupalKernel + \Drupal::service('cron')->run())

run in the fork child, and how much does the warm opcache buy?

  1. what does switching the Drupal stub tick from a cold drush spawn to the

fork-spawn endpoint change per tick?

Setup

  • Unit 1.36.1 (rootless, --otel build), PHP 8.4.25 + opcache, options.file php.ini

(opcache.enable=1, enable_cli=1, validate_timestamps=0).

  • Drupal 11.4.6 on SQLite, site FUTest.
  • PHP app spawnapp (fork_spawn.php, spare:1 max:1 idle_timeout:0) on 127.0.0.1:8816,

?job=cron|queue|sleep.

  • Trigger: curl 'http://127.0.0.1:8816/?job=cron' — the HTTP request returns at once,

the job runs in a detached fork child.

Effect of the warm opcache: total ≈0.42 s → ≈0.049 s (≈8.5×), kernel 0.11 → 0.011 (≈10×), cron 0.29 → 0.038 (≈7.5×). cron_ok=true, cron_result=true.

Two facts behind those two numbers:

  • cached_scripts freezes at 593 across ticks while hits grows monotonically

(1 → 594 → 1187 → 1780): every child compiles nothing new and everything it runs is a hit — the opcache SHM is genuinely shared between the worker, its forks and siblings.

  • Tick 1 is not cheaper than cold (0.41–0.48 s): the first child still pays the compile

of ~592 files into the SHM. The win starts at tick 2 and is permanent thereafter (idle_timeout:0 keeps that SHM alive as long as one worker lives).

Effect per tick: 0.52 s → 0.004 s (≈130×), and qualitatively different: the drush-mode tick blocks for PHP start + cold opcache fill + kernel + cron (a real drush adds its own bootstrap on top, so the shim is a lower bound), while the HTTP tick returns in ~4 ms and the job continues in the background child. A 3 s interval with a 0.52 s tick is 17 % of every period spent blocked; at 4 ms it is 0.13 %.

Measurement 3 — the stub tick with real Drush 13.8.0

Drush is no longer shipped as a phar: it is a Composer package installed inside the site (composer require --dev drush/drush; Composer itself needs ext-phar, which Alpine splits out of php84 — extract phar.so from php84-phar-.apk next to the other module .so files). Drush 13 refuses a global install ("must be installed inside a Drupal site"), and against a tree that only looks* like a project its preflight aborts with Package "drupal/core" is not installed.

Measurement 4 — queue drain (queue:run) cold vs warm

A real queue with a known per-item cost: harness module fu_queue_test (one #[QueueWorker], 1 ms sleep + a small CPU loop per item — so the work is separable from the tick's own cost), 50 items per drain, refilled before every run.

Child-side timing of the warm ticks: kernel_s 0.006–0.007, queue_s 0.170–0.196, total_s 0.177–0.203, cached_scripts 623, hits 2048 → 4562, queue_ok=true.

Reading: the tick's own cost (bootstrap) collapses and the trigger returns in ms, while the work itself barely moves — 50 items cost ≈0.18 s in every warm child (≈3.6 ms/item: the harness's 1 ms plus SQLite claim/delete round-trips). Warm opcache cannot make queue I/O cheaper; it only removes the per-tick start-up that used to be paid on top of it (0.26 s cold CLI, 0.68 s Drush).

A warm child adds ≈11 MB RSS on top of the parent's already-resident opcache pages (≈3.4 MB PSS, mostly shared): it does not re-pay the 36/57 MB a cold CLI / Drush process costs, and N children share one opcache SHM.

Bug found while measuring: exit() does not kill a fork child

With exit(0) in the children, each tick leaked 2 processes (the intermediate and the worker): inside a Unit PHP worker, exit() returns control to Unit's event loop instead of terminating, so the child keeps poll()ing and lives on as an extra "application" worker — it even accepts further requests (observed: process count 32 → 48 in 16 s; a leaked child served the health request of the next session).

Fix, verified (fork_spawn.php):

  • children die by posix_kill(getmypid(), SIGKILL) (zap()), never exit();
  • the request process reaps what it killed: reap() (pcntl_waitpid(-1, …, WNOHANG) drain)

before forking (clears the previous tick) and again after usleep(2000) (the SIGKILLed intermediate would otherwise stay a zombie held by the long-lived worker).

After the fix: process count flat, 0 zombies across 13 consecutive ticks; the ~2 ms reap sleep is inside the measured 3.4–4 ms trigger latency.

Restart hygiene (cost 2 wasted runs)

pkill-ing only the unitd main leaves controller/router/prototype/workers orphaned to init; they keep the listening socket and the next unitd dies with bind(127.0.0.1:8816) failed (98: Address in use) — the config then never applies and all requests go to the stale tree. start-fu-stand.sh now kills every unit: process and waits until the port is bindable before exec'ing unitd.

Also: opcache.validate_timestamps=0 means editing a stub needs a unitd restart — a running worker will keep serving the old compiled script.

Reproduce

  • bash tools/setup-fu-stand.sh /tmp/fu-pkgs (rebuild after /tmp is wiped; patchelf RUNPATH)
  • bash tools/start-fu-stand.sh /tmp/fu-pkgs (port 8816)
  • cold baseline: php84 -c php.ini apps/drupal_boot_cron.php (prints timing JSON on stderr)
  • warm: 4× curl 'http://127.0.0.1:8816/?job=cron', read cron_boot.out / spawn.out
  • stub: python app drupal_stub with TRIGGER=http|drush, CRON_INTERVAL=3, STUB_LOG=…

Caveats

  • Single-site stand (SQLite, no realistic content volume): the kernel/cron split is

representative, absolute cron time is not.

  • The trigger returns before the job finishes → the job outlives the request and nothing

supervises it; at-least-once needs a lock/dedup (Drupal's own queue lease or a lockfile).

  • \Drupal::service('cron')->run() re-enters the site's own state; concurrent ticks (two

triggers inside the same cron-window) are not deduplicated here.
