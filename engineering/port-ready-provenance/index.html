Which pid is the receiver-visible one (codex correction — this decides both the gate and the kill target)

nxt_process_t.isolated_pid (src/nxt_process.h:129) is always the pid as seen by the process that forked it: set at fork (src/nxt_process.c:337, :679), left alone by nxt_process_whoami_ok() (:902-910), while process->pid is rewritten to the global pid on PROCESS_CREATED (src/nxt_application.c:762-777 — which already matches cmsg_pid against isolated_pid), and the prototype's SIGCHLD also looks children up by isolated_pid (src/nxt_application.c:841-865, hash :1232-1241).

receiver ← processprocess->pidprocess->isolated_pidcmsg_pid
main ← prototype/core childglobal== globalglobal
non-isolated prototype ← workerglobal == localsamesame
pid-isolated prototype ← workergloballocallocal

Therefore the credential must equal isolated_pid only. The earlier "accept either" is a bypass: in a pid namespace another task whose ns-local pid numerically equals the victim's global process->pid passes; a compromised worker can fork toward such a collision.

Corrections to the issue text (read-verified, not runtime-confirmed):

  • Site 1 runs in the prototype, not main: libunit's READY goes to proto_port->pair[1] (src/nxt_application.c:1202-1207;

exec'd apps via src/nxt_external.c:113-125). Main hits the bug through site 2 — exactly the PR #212 repro.

  • Forgery is real: port sockets are per-owner, pair[1] is duplicated to every peer, msg->port->pid == nxt_pid always

(src/nxt_port.c:227-236, src/nxt_runtime.c:1914-1918); nxt_port_handler() (:257) dispatches on wire type only. Any worker can forge a READY naming a sibling and re-point the sibling's port->queue at attacker shm (src/nxt_port.c:530-549). Embedded modules also keep main's pair[1] (nxt_proc_keep_matrix[APP][MAIN], src/nxt_process.c:77-83, :369-386).

2. Options considered

  • (B) fail unconditionally — rejected: kill-any-start primitive for any worker; a silent refusal is #214-class — the RPC never

completes, pending_processes stays 1, with default processes: 1 (src/nxt_router.c:2057-2061) the app never starts again.

  • (C) mark READY then kill — rejected, but for a corrected reason: the worker's parent is the prototype, whose

nxt_proto_sigchld_handler() (src/nxt_application.c:825-921) sends REMOVE_PID whenever state ≠ CREATING (:907-909) and never clears stream on READY (the src/nxt_main_process.c:1108-1110 clearing cited before is main's handler — wrong site). The zero-delay respawn loop happens only if the bad port was broadcast and installed in the router: nxt_router_app_port_close() restarts at src/nxt_router.c:5390-5409 with no backoff. So: not-READY + no-broadcast is what prevents the loop; READY itself is merely wrong state.

  • (A) authenticate, then fail the start via the existing REMOVE_PID→RPC_ERROR path — chosen.

PR 2 (M) — fail the start on a refused queue [closes #231; site 1 only]

src/nxt_port.c else-arm :551, port->queue == NULL case only (:577):

  1. Do not set READY — move the assignment at :516 below the mmap (guard order at :498-509 says why).
  2. Skip nxt_port_send_new_port() at :596 — never broadcast an unreachable port.
  3. kill(process->isolated_pid, SIGKILL) — the receiver-visible pid (§0; process->pid is the global pid and would hit ESRCH or a

different process inside a pid namespace). SIGKILL, not SIGTERM: the worker has served nothing yet, and a compromised worker can ignore SIGTERM, leaving the RPC and pending_processes pending forever with no escalation. Log a failed kill() (ESRCH can be a legitimately already-pending SIGCHLD). Precedent src/nxt_process.c:696-703 uses the fork-returned pid — same identity rule. A port QUIT cannot work, by #231's own premise. Then existing plumbing fails the start (traced by codex, no leak/double-free found): descriptor closed once by nxt_port_recv_msg_close_fds (src/nxt_port.c:551-594, src/nxt_port.h:247-268) → prototype SIGCHLD finds the child by isolated_pid, sends REMOVE_PID (state CREATED ≠ CREATING, src/nxt_application.c:841-915) with the start stream (src/nxt_port.c:802-842), closes its ports → main closes its WHOAMI copy via nxt_port_remove_pid_handler() (src/nxt_port.c:864-895) → router: no peer to cancel (start RPC src/nxt_router.c:458-479 never calls nxt_port_rpc_ex_set_peer()), stream ≠ 0 → RPC_ERROR (:1111-1132) → nxt_port_rpc.c:361-417 deletes the registration once → nxt_router_app_port_error() :5054 → nxt_router_app_start_failed() :5092-5104 decrements pending_processes. The router never held the port (no broadcast). Later starts are request-driven (src/nxt_router.c:5637-5669) — same as a worker crashing at startup; no autonomous loop. Say so in the commit message rather than adding backoff.

Site 2 (nxt_main_new_port_handler) — explicitly NOT in PR 2. Closing/dropping main's copy does not fail the start: by the time NEW_PORT reaches main the prototype has already marked the worker READY and broadcast it, the router may be serving from it, and main already owns the port from WHOAMI (src/nxt_main_process.c:776-799; base handler src/nxt_port.c:383-420 keeps the queue fd). Dropping it turns "eventually wedges libunit" into "silently misses CHANGE_FILE/QUIT from main" — the SIGUSR1 acceptance would fail. And NEW_PORT has no provenance check, so a forged short-queue NEW_PORT from an embedded worker would trigger the destructive path. Keep the alert (#232) and fold the real fix into PR 3 (#223), which owns NEW_PORT provenance + validate-before-commit for router and main. If a stopgap is wanted: the mechanically safe removal is nxt_port_close() (src/nxt_port.c:154-190) + nxt_runtime_port_remove() (src/nxt_runtime.c:2066-2085) — but only behind a prototype-sender gate, and it still needs a policy to report the worker.
