TLS 1.3 and the cluster case — deep research (2026-10-11)

Question: what does TLS work have to deliver for 1.38, given that local networks and Kubernetes need TLS and preferably 1.3? Priority: 1.38.

Method: read the tree at origin/master, the TLS validation surface, the OpenSSL backend, the published docs, and the upstream issue archive. The stream plan A separate stream document owns the sequencing; this file owns the facts.

What the cluster and the local network actually need

At the edge, a proxy or ingress terminates TLS and the core needs nothing. Inside a cluster, pods talk to pods: the request arrives at the application server with TLS already on it because there is no proxy in the path (sidecars and service meshes are an option, not a given). That yields four requirements, in order of how often they decide an adoption:

  1. An explicit protocol policy. Cluster policy scanners and security baselines

want a field that says "TLS 1.2 minimum" or "TLS 1.3 only" and that fails at configuration time, not at the first handshake. conf_commands is a general escape hatch: keys are free-form, a typo is a runtime failure, and the field is not in the schema a scanner reads.

  1. Client certificates for service-to-service auth. Short-lived certificates from

a cluster CA (SPIFFE identifiers, step-ca, cert-manager) are the mesh-less way to authenticate a caller. The backend can verify them; nothing in the configuration surface asks for it, and the verify depth is pinned to 1 with a TODO.

  1. Rotation without a restart. cert-manager rewrites a mounted secret. What the

operator needs is a documented, atomic replacement path, and a clear statement of who triggers it (a control API call, not a file watcher).

  1. TLS 1.3 semantics that hold. 1.3 removed renegotiation and the session cache

works differently; tickets carry the resumption. Whatever the configuration says must hold on 1.3 too, and 0-RTT must be refused on purpose rather than inherited from a library default.

Small image, read-only rootfs and health probes are already satisfied or covered by other work, and are not part of this list.

Recommended 1.38 scope

P0 — a TLS object that says what it means. Add first-class members beside certificate: a minimum and maximum protocol version, a TLS 1.3 cipher suite list, and the pre-1.3 cipher list. Keep conf_commands for everything else. Rationale: this is what a cluster manifest and a policy scanner consume; it is also the smallest change that closes the "preferably 1.3" ask in a reviewable way.

P0 — the client CA member, wired to the existing path. Expose the CA certificate and the verification policy (off / request / require) plus a configurable depth, and give the two TODOs a real callback. Rationale: mTLS is the mesh-less answer, and the backend already does the hard part.

P1 — the TLS module carries 1.3 and the h3 ALPN token. The module interface (W1, pull request 23) must treat 1.3 as a first-class version and h3 as a first-class protocol value. Rationale: QUIC requires 1.3, so the HTTP/3 track cannot start without it. This is the only hard coupling between the two tracks.

P1 — rotation, documented end to end. State the contract: which control API call replaces a bundle, what happens to connections in flight, and how a mounted secret becomes a new bundle. Add a test that replaces a bundle while requests are running.

P2 — refuse 0-RTT explicitly. When 1.3 is on, early data must be off by default with a documented reason (replay), rather than depending on the library default.

Deferred, with the reason on record: OCSP stapling (operators terminate at a proxy that staples), ECH, post-quantum groups, per-SNI protocol policy. Each has a dependency or a cost that does not fit the 1.38 window.

What must be verified before any claim

  • Whether a client CA is reachable today through a documented surface (certificate

as an array is documented for SNI bundles; the client-CA path needs a check of its own before anyone writes "mTLS is supported").

  • The lowest OpenSSL the build accepts, because conf_commands and therefore the

only current route to 1.3-only depends on OpenSSL 3 conf command support, and the validator marks the member unsupported when the library lacks it.

  • That the rotating-bundle path is atomic under load, not only that the API returns

success.

Do not claim

  • Do not present conf_commands as a supported TLS 1.3 configuration. It is a route

that works; it is not a feature.

  • Do not claim mTLS, OCSP stapling, 0-RTT or per-SNI policy support.
  • Do not put a version number or a date on any of the P0 to P2 items in public text

before the code lands.

Prior art

The upstream issue archive carries no demand thread for TLS 1.3 and no SNI request — the mentions of Kubernetes are incidental, inside unrelated reports. The consequence is worth stating plainly: the cluster case is not an upstream backlog item that can be inherited; if it is wanted, it is written here.
