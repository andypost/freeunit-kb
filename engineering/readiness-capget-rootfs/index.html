Why so many PRs came out of capget/rootfs (snowball / class effect)

_2026-09-06 observation. 33 PRs in window 250-293; only 6 are directly capget/ rootfs. The rest are the connected-defect class the two P0s opened._

Capget is not one bug — it is a class on one contoured path (capset/capget/fork/cred + the same IPC port/process path):

  • #254 capability fallback (the fix itself)
  • #255 clear proto_port_requests (process-start path)
  • #253 port auth by kernel pid (adjacent same port/process path)

Rootfs is not one bug — 4 axes, 4 PRs (mount ns + automount + memfd + cred):

  • #259 test-side (timezone db)
  • #265 product fix (automount.language_deps)
  • #278 build fix (memfd_create probe, musl/Alpine)
  • #279 config reject (rootfs+credential w/o mount ns)

Why it snowballs (root cause, not a bug):

  • capget & rootfs are SYSTEMIC problems (cap visibility, mount-namespace, build

detection). Fixing a systemic defect opens N adjacent defects on the same contour, not one isolated case.

  • The 09-05 wave (#277-291) is NOT all capget/rootfs — it is clearing adjacent

defects found en route (router listener, http compression, access-log, state files, START_PROCESS reply, app-start bound). Same PORT/PROCESS/ROUTER/HTTP zone, but distinct defects.

  • Small verifiable PRs (one per change) is the CORRECT practice — not one

giant PR. 33 small PRs ≠ noise; #284 (access-log), #287 (port lock), #281 (engine-quit job) each carry a real fix.

Classification (250-293): capget/rootfs direct = 6 · CI/test/build = 9 · adjacent (port/process/router/http) = 18.
