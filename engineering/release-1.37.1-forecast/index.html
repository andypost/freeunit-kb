Forecast (hypotheses, not commitments)

  • Content: 1.37.1 ships as a bugfix patch — no Feature and no API/breaking Change is

in the section today, and the wasm/websocket/chunked fixes are the kind that a patch carries. Hypothesis: 20–30 CHANGES entries at the release commit, dominated by Bugfix, with 0–3 Security entries depending on whether the open 2026-10-03 audit items land.

  • Volume at release, if the cycle closes inside the next 3–10 days (from the measured

rate, no plateau assumed): 95–140 commits, 65–95 merged PRs, +11 000–17 000/−1 500–3 000 lines, tests ≈45–50% of insertions.

  • Date: earliest defensible date is 2026-10-11 (the "security fix ≤7 days" rule, 7 days

after 1.37.0); the realistic window is 2026-10-12 … 2026-10-18, gated on the release steps that 1.37.0 needed (CHANGES date + version bump release commit, docs-site update, unitctl tag).

  • Comparability: the 1.37.1 cycle is a patch cycle, so its churn cannot be compared to

1.37.0 (a batch-merge release day carrying 211 PRs); the useful comparison is 1.36.1.

The 1.37.x shortlist (checked 2026-10-11)

A patch release carries security and severe-regression fixes only. Inside that rule three open issues fit the line, each small enough for one review wave:

  • #537 — http: the body-read deadline restarts on every read, so a slow client

keeps a request alive indefinitely. Fix: one absolute deadline per request body.

  • #538 — http: route regexes are matched without PCRE2 match, depth or JIT-stack

limits. Fix: set the limits at match time; a configuration member is optional.

  • #539 — http: the concurrent-connection ceiling is a hardcoded 256. Fix: make

the limit a known, documented value.

All three carry no label today; the label is what the release process reads, so labelling them is the first step. Attempted 2026-10-11 and blocked: the automation account (the GitHub App used for writes) is installed on freeunitorg/freeunit-exp only — /installation/repositories returns exactly one repository — so it gets 403 creating or applying a label in freeunitorg/freeunit. There is no z-security label in the main repository either. Two ways out: install the App on the main repository, or apply the labels by hand. Until then these three stay invisible to the release process; the shortlist itself is recorded in the release-train discussion (freeunit-exp #12) so it is not lost.

Do not hold the 1.37.1 tag for them: ready inside the window they ride with 1.37.1, otherwise they take the next patch release alone.

#632 (no 32-bit CI job) is infrastructure, not release content, but it guards the class that already produced two 32-bit bugfix entries in the 1.37.1 block (the off_t and the size-arithmetic fixes) — worth landing in the same window.

Features that stay out of the 1.37 line: HTTP/2 stack (#463, #467, #470, #471, #479, #483, #484), router schedules (#452), USDT probes (#451), read-only status socket (#460), router match extensions (#461), opt-in PCRE2 JIT (#551).

The same shortlist is public in STREAMS.md of freeunitorg/freeunit-exp (pull request 21), which is where the stream state lives now.

Blockers and risks for 1.37.1

  • No Security entry yet while the 2026-10-03 audit issues stay open: #537 (body-rate

floor / slow-POST hold), #538 (PCRE2 limits → remote ReDoS), #539 (hardcoded 256 concurrent-connection ceiling), #540, #541. Hypothesis: either one of these lands and makes 1.37.1 a security patch, or the release ships as bugfix-only — which sits outside the stated "patch = security/DoS fixes only" policy and is worth an explicit decision.

  • #632: no CI job compiles a 32-bit target, so a 32-bit-only -Werror survived into 1.37.0;

the fix is in this cycle but the gate is still missing.

  • #624: test_asgi_websockets_message_over_buffer_limit hangs on s390x (blocking sendall,

no timeout) — a flaky-red risk for the release CI.

  • Release steps still pending: CHANGES date + version bump, docs-site/changes.xml polish

(the 1.37.1 stanza is still dated 2026-10-04 with an empty-looking revision), unitctl tag.

  • 20 of 35 open PRs carry no label, and none carries a security label — triage visibility is

weaker than the queue size suggests.
