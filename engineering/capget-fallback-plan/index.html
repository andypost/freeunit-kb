2. Code change (S) — narrowed after codex review

Why not "unknown → none, always": with setid == 0 the runtime never resolves credentials (src/nxt_runtime.c:874-885) and never calls setgid/setuid (src/nxt_process.c:1100-1120); app user/group are only string-compared against the --user/--group strings (src/nxt_isolation.c:100-128, default app user copied from the string at src/nxt_main_process.c:554-557). Unit never calls capset(). So a non-root unitd that does hold CAP_SETUID/SETGID (systemd ambient/file caps) but whose capget is filtered would silently keep its own uid for every app while the config says otherwise, and would keep the unobservable capabilities. That is the existing "unprivileged" mode, not an escalation — but it is a silent downgrade, and "continues as an unprivileged process" would be a false CHANGES line.

src/nxt_capability.c, nxt_capability_specific_set(), the nxt_capget(&hdr, val) == -1 branch:

  • errno == EPERM || errno == ENOSYS (the filter signatures) → NXT_LOG_WARN: `"capget() is blocked (%E); capabilities are unknown and

will not be used: user/group switching and rootfs are disabled, applications run as uid %d" → return NXT_OK` (flags stay 0).

  • any other errno (EINVAL/EFAULT = version/invariant bug) → keep the existing alert + NXT_ERROR.
  • Do not touch nxt_runtime.c:870. The "Unit is running unprivileged" warn at :882-884 still fires after the fallback — acceptable,

the new warn precedes it and says why.

  • Version probe nxt_capability_linux_get_version() already ignores failure — leave it. #else (non-Linux) arm untouched

(src/nxt_capability.c:123-129 returns NXT_OK with zero flags — same shape as the fallback).

  • Optional hardening in the same PR (decide at implementation): on the fallback path, compare the configured --user with the actual

geteuid() name and warn explicitly when they differ — that is the case codex flagged.

  • Residual, documented in the commit message and CHANGES: unobservable capabilities are not dropped. Codex P1 on 9f0e5db0 proposed

capset(0) on the fallback path; rejected for this PR (verified 2026-08-30): nxt_capability_set() runs in main from nxt_runtime_conf_init() (src/nxt_runtime.c:125→870) but main binds listeners later, in nxt_main_listening_socket() (src/nxt_main_process.c:1294, bind() at :1345, called from the SOCKET handler :1240) — dropping everything in main would strip CAP_NET_BIND_SERVICE, the one real systemd scenario, turning "fails at start" into "starts but cannot listen on :80". Capget being filtered means we cannot choose what to drop. See §4 item 5 for the correct place. Fail-closed remains for non-filter errnos.

  • Note (src/nxt_isolation.c:637-651): chroot == 0 rejects rootfs configs (loud), and a NEWUSER (credential) namespace

overrides both flags (:94-97, :642-645, src/nxt_process.c:1102-1107) — so the warn/CHANGES text must be qualified: "disabled for applications that do not enable the credential namespace". (Review 2026-08-30 caught the unqualified wording in 9f0e5db0.)

  • The warn is emitted from nxt_runtime_conf_init() (src/nxt_runtime.c:125→870) BEFORE unit.log is opened

(nxt_runtime_log_files_create, :356), so it only reaches stderr — verified empirically. Record a flag and re-emit after the log opens, or the "silent downgrade" rationale only holds for foreground starts; the smoke test must assert on unit.log after that fix.

3. Tests (honest scope)

  • pytest cannot mock syscalls; LD_PRELOAD cannot intercept syscall(SYS_capget) (src/nxt_capability.c:35-36); a Docker seccomp

profile kills runc. Not viable in-suite.

  • Viable: secexec.c wrapper in tools/ of freeunitorg/freeunit-harness: prctl(PR_SET_NO_NEW_PRIVS) + SECCOMP_MODE_FILTER BPF returning

SECCOMP_RET_ERRNO|<errno> for SYS_capget, errno selectable (EPERM and ENOSYS both exercised), with an AUDIT_ARCH check (compile SYS_capget per target; omitting the arch check is unsafe across compat ABIs, not "portable"). Dynamic link is fine; -static only if the runner lacks the libc.

  • Run build/sbin/unitd --no-daemon unprivileged under it with the same temp --statedir/--pid/--log/--control/--tmpdir the suite

uses (test/conftest.py:493-513) — a bare invocation fails on filesystem perms before reaching the fallback.

  • Assert: new [warn] present; router started; load a trivial app and check its actual uid/gid/groups (/proc/self/status

via a python app) — the control-socket 200 alone does not cover the downstream path codex flagged. Two variants: (a) no caps + filter (must start, app uid == unitd uid); (b) with CAP_SETUID/SETGID granted (e.g. capsh/file caps or systemd AmbientCapabilities) + filter — documents the residual: starts with the warn, app uid == unitd uid, no escalation.

  • Non-filter errno path: not testable without fault injection; covered by code review.
  • Regression: test/test_go_isolation_rootfs.py, test/test_java_isolation_rootfs.py, test/test_python_isolation_chroot.py,

test/test_python_isolation.py (test_rootfs as a file does not exist).

  • Alternative where a systemd user session exists: systemd-run --user -p SystemCallFilter=~capget -p SystemCallErrorNumber=EPERM.
